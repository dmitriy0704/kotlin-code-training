# 33. Search in Rotated Sorted Array

## Условие

Имеется целочисленный массив nums, отсортированный в порядке возрастания (с
уникальными значениями).

Перед передачей в вашу функцию массив nums может быть повернут влево в
неизвестном индексе k (1 <= k < nums.length), так что результирующий массив
будет иметь вид [nums[k], nums[k+1], ..., nums[n-1], nums[0], nums[1], ...,
nums[k-1]] (с индексацией 0).

Например, [0,1,2,4,5,6,7] может быть повернуто влево на 3 индекса и
стать [4,5,6,7,0,1,2].

Получив массив nums после возможного поворота и целочисленное значение target,
верните индекс target, если он находится в массиве nums, или -1, если он не
находится в массиве nums.

Вам необходимо написать алгоритм со сложностью выполнения O(log n).

Example 1:
Input: nums = [4,5,6,7,0,1,2], target = 0
Output: 4

Example 2:
Input: nums = [4,5,6,7,0,1,2], target = 3
Output: -1

Example 3:
Input: nums = [1], target = 0
Output: -1

Constraints:

1 <= nums.length <= 5000
-104 <= nums[i] <= 104
All values of nums are unique.
nums is an ascending array that is possibly rotated.
-104 <= target <= 104

## Решение

Разбираем задачу 33. Search in Rotated Sorted Array (поиск в циклически
сдвинутом отсортированном массиве)

Ты правильно заметил, что это классическая «бинарно-поисковая» задача, но с *
*изюминкой** — массив был отсортирован по возрастанию, а затем **повёрнут** (
сдвинут) в какой-то позиции. Например:

- Было: `[1, 2, 3, 4, 5, 6, 7]`
- Повернули на 3 позиции вправо → получили `[5, 6, 7, 1, 2, 3, 4]`

Такой массив уже не является монотонно возрастающим, но у него есть свойство: он
состоит из **двух отсортированных частей**, и разрыв находится в одном месте.

Наша задача — найти индекс `target` за O(log n), не прибегая к линейному поиску.

### Главная идея решения

В бинарном поиске мы всегда делим массив пополам и смотрим на средний элемент
`nums[mid]`. В обычном отсортированном массиве мы сразу знаем, в какой половине
искать. В повёрнутом — мы не можем так просто решить, потому что
последовательность нарушена.

Однако **одна из половин обязательно является полностью отсортированной** (по
возрастанию). Это ключевой факт. Мы можем определить, какая половина
отсортирована, сравнив `nums[left]` и `nums[mid]`:

- Если `nums[left] <= nums[mid]` → левая половина `[left..mid]` отсортирована.
- Иначе (т.е. `nums[left] > nums[mid]`) → правая половина `[mid..right]`
  отсортирована.

После того как мы поняли, какая половина упорядочена, мы проверяем, лежит ли
`target` в этой упорядоченной половине. Если да — мы отбрасываем другую
половину. Если нет — мы отбрасываем эту упорядоченную половину и ищем в другой (
которая тоже может быть частично упорядочена, но мы её обработаем на следующей
итерации).

### Алгоритм по шагам

1. Устанавливаем `left = 0`, `right = nums.size - 1`.
2. Пока `left <= right`:
    - `mid = left + (right - left) / 2`
    - Если `nums[mid] == target` → возвращаем `mid`.
    - **Определяем, какая половина отсортирована:**
        - Если `nums[left] <= nums[mid]` → левая половина отсортирована:
            - Проверяем, попадает ли `target` в диапазон
              `[nums[left], nums[mid])` (т.е.
              `target >= nums[left] && target < nums[mid]`).
            - Если попадает → ищем в левой половине: `right = mid - 1`.
            - Иначе → ищем в правой половине: `left = mid + 1`.
        - Иначе (правая половина отсортирована):
            - Проверяем, попадает ли `target` в диапазон
              `(nums[mid], nums[right]]` (т.е.
              `target > nums[mid] && target <= nums[right]`).
            - Если попадает → ищем в правой половине: `left = mid + 1`.
            - Иначе → ищем в левой половине: `right = mid - 1`.
3. Если вышли из цикла — возвращаем `-1`.

### Реализация на Kotlin

```kotlin
class Solution {
    fun search(nums: IntArray, target: Int): Int {
        var left = 0
        var right = nums.lastIndex

        while (left <= right) {
            val mid = left + (right - left) / 2

            if (nums[mid] == target) return mid

            // Левая половина отсортирована
            if (nums[left] <= nums[mid]) {
                // target лежит в левой упорядоченной части?
                if (target >= nums[left] && target < nums[mid]) {
                    right = mid - 1  // ищем слева
                } else {
                    left = mid + 1   // ищем справа
                }
            }
            // Правая половина отсортирована
            else {
                // target лежит в правой упорядоченной части?
                if (target > nums[mid] && target <= nums[right]) {
                    left = mid + 1   // ищем справа
                } else {
                    right = mid - 1  // ищем слева
                }
            }
        }
        return -1
    }
}
```

### Разбор примера

Возьмём `nums = [4, 5, 6, 7, 0, 1, 2]`, `target = 0`.

- `left = 0, right = 6, mid = 3` → `nums[mid] = 7` (не равно).
- `nums[left] = 4 <= 7` → левая половина `[4,5,6,7]` отсортирована.
- Проверяем: `target = 0` лежит ли в `[4, 7)`? Нет. Значит, идём в правую
  половину: `left = 4`.
- Теперь `left = 4, right = 6, mid = 5` → `nums[mid] = 1` (не равно).
- `nums[left] = 0 <= 1` → левая половина `[0,1]` (от 4 до 5) отсортирована.
- Проверяем: `target = 0` в `[0, 1)`? Да, `0 >= 0 && 0 < 1` → ищем слева:
  `right = 4`.
- Теперь `left = 4, right = 4, mid = 4` → `nums[mid] = 0` → возвращаем `4`.

### Почему это работает?

На каждой итерации мы точно определяем, какая половина массива отсортирована.
Затем мы либо находим `target` в этой половине (и продолжаем поиск там), либо
понимаем, что его там нет (и тогда он гарантированно находится в другой
половине, потому что все элементы в упорядоченной половине мы уже исключили).
Таким образом, мы всегда отбрасываем половину массива, сохраняя сложность O(log
n).

### Важные нюансы

- **Равенство элементов** — в задаче 33 все элементы уникальны, поэтому условие
  `nums[left] <= nums[mid]` строгое. Если есть дубликаты (задача 81), условие
  `<=` может привести к неопределённости, когда
  `nums[left] == nums[mid] == nums[right]`; тогда нужно обрабатывать отдельно,
  сдвигая `left++`.
- **Границы сравнения** — при проверке попадания `target` в отсортированный
  интервал используй **строгие/нестрогие** неравенства в зависимости от того,
  включены ли концы. В коде выше для левой половины мы используем
  `target >= nums[left] && target < nums[mid]`, то есть левая граница включена,
  правая — исключена, потому что `nums[mid]` мы уже проверили. Для правой —
  `target > nums[mid] && target <= nums[right]`, аналогично.
- **Крайний случай** — если массив не повёрнут, т.е. просто отсортирован,
  алгоритм всё равно работает, потому что левая половина всегда будет
  отсортирована и мы будем проверять `target` в ней, как в обычном бинарном
  поиске.

### Альтернативный подход (через поиск точки поворота)

Можно сначала найти индекс минимального элемента (точку поворота) с помощью
бинарного поиска, а затем применить обычный бинарный поиск в нужной половине.
Этот способ требует двух проходов, но тоже O(log n). Однако однопроходный
метод (описанный выше) проще и компактнее, поэтому он считается стандартным для
этой задачи.

## Дополнительно:

Отличный вопрос! Ты правильно заметил, что в повёрнутом массиве действительно
есть **две отсортированные части** (если смотреть по точке разрыва). Например, в
`[5,6,7,0,1,2,3,4]` — это `[5,6,7]` и `[0,1,2,3,4]`, и каждая из них
отсортирована по возрастанию.

**Но** в бинарном поиске мы делим массив не по точке разрыва, а **по середине
** (индексу `mid`). И вот тут ключевой момент: когда мы берём `mid`, левая и
правая половины (от `left` до `mid` и от `mid` до `right`) **не обязательно**
будут соответствовать этим двум отсортированным кускам.

Давай разберём на примере.

---

### Пример: `nums = [5, 6, 7, 0, 1, 2, 3, 4]` (длина 8)

Индексы: `0:5, 1:6, 2:7, 3:0, 4:1, 5:2, 6:3, 7:4`

#### Ситуация 1: `mid = 3` (элемент `0`)

- Левая половина: `[5, 6, 7, 0]` — она **не** отсортирована (убывание в конце).
- Правая половина: `[1, 2, 3, 4]` — она **отсортирована**.

#### Ситуация 2: `mid = 1` (элемент `6`)

- Левая половина: `[5, 6]` — отсортирована.
- Правая половина: `[7, 0, 1, 2, 3, 4]` — не отсортирована.

#### Ситуация 3: `mid = 5` (элемент `2`)

- Левая половина: `[5,6,7,0,1,2]` — не отсортирована.
- Правая половина: `[3,4]` — отсортирована.

**Вывод:** при любом `mid` **одна из половин (левая или правая) обязательно
будет полностью отсортирована по возрастанию**, а другая — может быть
неотсортированной (или тоже отсортированной, если точка разрыва не попала в эту
половину). Это свойство и используется в алгоритме.

---

### Зачем нам это знать?

В обычном бинарном поиске мы сравниваем `target` с `nums[mid]` и решаем, идти
влево или вправо, потому что весь массив отсортирован. Здесь же мы не можем
просто сравнить, потому что массив не монотонный. Но мы можем **проверить, лежит
ли `target` в пределах отсортированной половины** (по её минимальному и
максимальному значению). Если да — мы знаем, что искомый элемент точно в этой
половине, и можем отбросить другую. Если нет — значит, его там нет, и он должен
быть в другой половине (которая, возможно, тоже частично упорядочена, но мы
разберёмся с ней на следующем шаге).

---

### Пошаговый разбор на примере поиска `target = 0`

- `left = 0, right = 7, mid = 3` → `nums[3] = 0` — мы сразу нашли! Но для
  примера пусть ищем `1`.

#### Ищем `target = 1`

1. `left=0, right=7, mid=3` (`nums[3]=0`).
    - `nums[left]=5 <= nums[mid]=0`? **Нет** (5 <= 0 — ложно). Значит, левая
      половина **не** отсортирована, а значит, правая половина (`[1,2,3,4]`)
      отсортирована.
    - Проверяем, лежит ли `target=1` в правой упорядоченной части:
      `target > nums[mid] && target <= nums[right]` → `1 > 0 && 1 <= 4` → *
      *истина**.
    - Значит, искомый элемент находится в правой половине. Отбрасываем левую:
      `left = mid + 1 = 4`.
2. Теперь `left=4, right=7, mid=5` (`nums[5]=2`).
    - `nums[left]=1 <= nums[mid]=2` → истина → левая половина (`[1,2]`)
      отсортирована.
    - Проверяем `target=1` в левой части:
      `target >= nums[left] && target < nums[mid]` → `1 >= 1 && 1 < 2` → истина.
    - Ищем в левой: `right = mid - 1 = 4`.
3. `left=4, right=4, mid=4` (`nums[4]=1`) → нашли, возвращаем `4`.

---

### Почему нельзя просто искать в двух отсортированных частях?

Теоретически можно: сначала найти точку разрыва (индекс минимального элемента)
за O(log n), а затем применить обычный бинарный поиск в одной из двух половин.
Но это потребует двух проходов. А данный алгоритм делает всё **за один проход**,
используя тот факт, что при каждом делении пополам одна из половин всё равно
упорядочена. Это более элегантно и часто проще в реализации.

---

### Резюмируя

- В повёрнутом массиве есть **два упорядоченных сегмента**, но при бинарном
  поиске мы делим массив по середине, и получаем **одну отсортированную половину
  ** (левая или правая).
- Мы проверяем, попадает ли `target` в эту отсортированную половину по её
  крайним значениям. Если попадает — продолжаем поиск в ней, иначе — в другой
  половине.
- Это позволяет сохранить сложность O(log n) без дополнительных проходов.
